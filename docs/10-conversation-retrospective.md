# 从最初安装到 HDMI 2 的完整对话回溯

最开始只是想装 Google 商店和 Clash，后来逐步变成一套围绕遥控器、桌面、语音和电脑接线的日常使用改造。这里按需求出现的先后，补上为什么换方案、哪些办法失败过，以及最终由谁确认了什么。日期使用北京时间，范围为本项目 2026-11-03 至 2026-11-24 的对话和对应实机记录。

当前结果见[折腾总结](09-conversation-summary.md)，逐项验收见[验证状态](00-status.md)。历史中的早期反馈不替代后来的复测结果。

## 11 月 3 至 4 日 从装商店和 Clash 改成用电脑代理

最初的要求是在已开启 ADB 的投影仪上安装 Google 商店和 Clash。连接地址先纠正过一次，后续还因 DHCP 变化多次更新。因此，最早就出现了“地址会变”这个环境条件。

Clash 配置导入时，先提供的是服务名称，后来补充订阅链接。接着用户改变方向：“或者不要 clash 了，给我设置代理到电脑上就行了。”后续按这个选择处理，结束投影仪端 Clash 路线，改用电脑已有代理的局域网入口。订阅、服务编号、真实地址和截图不在公开记录中保留。

Google 组件和商店装好以后，商店能进入初始登录界面，但登录请求失败。排查发现电脑端加速工具曾干预 `fonts.gstatic.com` 的 hosts 和 TLS 证书。用户自行关闭相应工具后，域名连通探测恢复。**这一步确认的是访问链路改善，账户登录完成和设备认证没有得到确认。**

次日用户要求把代理做成桌面应用，明确说要“默认关闭，并且可以后台使用”。实际做法是打开应用即启用系统 HTTP 代理，退出界面后继续保留，按钮可以关闭；开机接收器按默认关闭实现。开关、HTTPS 连通和退出后保留做过检查，开机默认关闭当时没有单独完成一次重启验收。它也不等于为每一个应用提供 VPN 接管。[应用与代理详情](06-apps-proxy-drm.md)

## 11 月 4 日 Apple TV 装上以后还有两个不同问题

Google 组件安装后，用户要求再装 Apple TV。随后发现“装了为什么桌面看不到”，于是补了一个适合电视桌面的启动入口。这个入口负责打开原应用，解决的是找不到入口的问题。

接着出现“无法加载视频”。临时开代理后，用户仍反馈同一错误。后来检测到设备 Widevine L3，以及 L1 信任和 Keybox 相关异常；独立 DRM 检测程序自己的会话也有未预配结果。但没有拿到 Apple TV 自身的许可证错误码，不能把这些观察写成已证明唯一根因。

所以这条线的结果一直分四层记录：**安装成功、有桌面入口、应用能启动、正片能播放**。前三层有进展，第四层没有解决。DRM 观察出现在后续按需 root 试验之前，也不能倒过来说是后面的 root 导致了早期播放失败。[播放诊断与边界](06-apps-proxy-drm.md)

## 11 月 6 日 用户真正要求的是重启后仍然好用

新一轮问题是音量只能看到十几档，低档也太响；第三方桌面装好了，遥控器 Home 却回原厂首页。用户进一步问能否取得固件直接修改，因为一些 ADB 设置重启后就没了。

目标随后明确为两件事：遥控器音量加减要细到 1～100；Home 一次直接到自己安装的当贝桌面，不经过厂商选择器。用户允许为持久化做必要修改，同时要求在每次修改前解释：**为什么做、会有什么后果、具体怎么做。**

因此先检查权限与恢复手段。普通 ADB shell 和 `adb root` 的限制仍在，但通过这份固件已有的诊断入口，验证了短时执行 root 任务的能力。后续采用按需提权、加载运行时补丁和恢复 SELinux 内存策略的路线，没有安装 Magisk，也没有刷写修改过的 boot 或系统镜像。系统只读分区、原有验证状态与实际 root 能力分别记录，不能由其中一项推断另外几项。[设备与 root 记录](01-device-and-root.md)

这里的“持久化”是正常开机后自动恢复配置和补丁。没有承诺 OTA、恢复出厂、卸载工具或手动强行停止后仍无条件生效。

## 音量经历了按键和实际响度两条排查线

最早看见粗档位，容易把音量条数字当成系统音量上限。检查后发现系统媒体音量范围已经是 0～100，而厂商按键、音量条和喇叭增益另有处理。

早期试过资源覆盖与普通音量键接管。普通键额外拦截会和原处理叠加，试验的资源覆盖后来撤销。最终只给这支遥控器的两个音量键设置专用 KL/IDC 映射，再由自写无障碍服务处理每次一格、长按连续和松手停止，同时显示自己的百分制音量条。用户还反馈过“现在是 1～20”，促使继续核对原厂显示和实际事件，而没有把第一次安装成功直接当作完成。

早期的注入按键验证与后来的实体遥控器确认是分开记录的。用户最初说“可以了”以后，重启和任务清理仍暴露过新故障。[按键与保活实现](02-remote-home-background.md)

11 月 8 日，用户又报告无反应、延迟跳动、低档过响，以及回到同一格听起来不一致。检查发现遥控服务虽挂着前台服务，仍被固件降到低调度状态，积压的按键后来集中执行。先补了过期事件丢弃和单包调度保护，解决的是响应与补执行问题。

但用户继续反馈响度不对。固定标准音效后只“稳定了些”，没有消除跳变。进一步追踪内置喇叭 HAL，重复 5→6→5→6，并延后取样到 2.5 秒，发现原映射的实际增益仍会反向变化。随后试用 −75 dB 到 0 dB 的单调曲线，0 保留原静音路径。用户明确确认：“平稳了，低档也合适。”才安装开机自动加载版，并完成两次完整重启验证。

最终加载时先静音，确认补丁 ready 且 SELinux 内存策略恢复后，再恢复原音量。曾试验关机广播静音，后来确认本机重启没有送达预期通知，已撤掉这个无效方案。新的曲线解决的是系统档位与增益关系；没有进行片源 LUFS 归一化或麦克风声压测量。[曲线数据](../data/volume-curve-validation.json)

## Home 能返回和开机直接进入是两种验收

设置普通默认桌面后，仍遇到厂商选择器，随后改为登记两类持久 HOME intent。用户一度确认 Home 正常，但后来又指出：“点击遥控的桌面键是可以去当贝桌面的，但是重启后就不行。”

这区分了两条链路：按 Home 的 intent 解析，以及开机时厂商主动启动自己的首页。后者不是改一个默认项就一定消失。方案先补受控的开机、亮屏检查窗口，避免在 HDMI 正在播放或其他应用已在前台时抢界面；后来用户要求禁用默认桌面，再只停用原厂 HOME/LAUNCHER 首页组件。

原厂服务、provider 和系统备用 Home 继续保留。最终用户在完整重启后确认“是，直接进入当贝桌面”。这也说明“只保留当贝桌面”落到实施时，采用的是有恢复路径的首页组件处理，而不是卸载整个原厂系统包。[Home 与恢复说明](02-remote-home-background.md)

## 杀后台没有被描述成一次性全部关闭

用户描述第三方应用“都有，只有固件自带的软件不会”。早期关闭额外的短时强停开关，不代表所有独立名单和正常 Android 回收都停止。

后来还出现工具被移出任务后停止、无障碍配置被清空，以及前台服务仍遭低优先级调度的情况。才陆续加入前台服务、开机恢复、无障碍自恢复、过期按键丢弃，并只为 `local.tvkeys` 加包级 adj 100。

另有一层独立防护，只拦截 Etna 对遥控优化和第三方当贝桌面的特定强停调用。没有把播放器、Google 服务、所有第三方应用都设为不可回收，也没有取消系统正常内存管理。用户手动强停仍是需要区分的行为。[后台和厂商限制](05-performance-and-restrictions.md)

## 语音从只回答好到执行和自动退出

用户最常用的是调亮度，并明确要的是**投影灯的光源亮度**，不是画面亮度参数。先做实际光强验证：1→2 差别不明显，用户要求调到 10，再要求保持 30 秒，观察确认后才继续语音执行。

需求随后加上打开应用。识别文字接收试验一开始没有反应，用户多次要求重新开测试，最后改为复用原助手进程内的识别和播报链路；ARMv7 的 Java 桥兼容问题也在这一阶段处理。后来实体语音调光、打开 Apple TV 和反馈都确认成功。

但执行成功后面板不会自己退，用户还要按返回。第一次处理后仍未退出，继续修到面板及左下角悬浮头像都消失，用户才回复“好了”。这条线的验收包含识别、执行、反馈和退出，不只检查命令是否到达。

安装自动加载前，说明了每次开机或原服务重启后短时 root 加载、恢复策略、后台检查与内存开销，用户明确同意安装并重启验证。v4 的完整语音流程通过了整机和助手进程重启验证，v5 新增切源命令的验收另计。[语音实现与测试](03-voice.md)

## 显示需求从所谓扩展变成按实际输入源单屏

最初电脑接着笔记本内屏、外接显示器和投影仪，用户把目标叫“扩展”，但实际描述是另外两屏都关、只亮投影仪。这不属于传统的多屏扩展桌面，因此第一步保存了仅投影仪的 Windows 布局，关开测试一度通过。

随后用户补清楚了两个使用场景：投影仪还在自己的系统时，电脑只亮外接显示器；投影仪手动切到电脑 HDMI 后，才只亮投影仪。笔记本内屏正常关闭。于是“设备在线就只亮投影仪”的办法不够用了。

用户又指出投影仪没有固定 IP，不适合长期靠固定 ADB 地址。明确接受同一局域网自动发现后，方案才变成投影端只读状态应答、Windows 根据经过配对校验的真实源状态选屏。原 HDMI 1 的实体往返是在主动断开 ADB 后确认的。

投影仪自己的自动选源与电脑选屏也分开处理。用户曾希望默认留在系统、自己选择输入，并提出语音切源，随后叫停继续折腾。历史本机设置已关闭 HDMI 自动选源，并把开机源设为系统；v5 语音切源只记录到代码加载，没有实体验收，不能把后来的 Windows 自动选屏当作它的验证。[两端联动](04-display-router.md)

## 黑屏后才把 Windows 后台改为计划任务

后续投影仪重启时出现电脑黑屏，用户拔掉 HDMI 才恢复，并说明电脑此前也重启过。排查时后台没有在运行，已有日志没覆盖黑屏瞬间。因此记录保留为一次未完整还原的事故，没有武断归为某一条指令。

排查同时找到了明确的条件错误：旧逻辑会只凭缓存源编号切屏，即使 HDMI 播放标记没有确认正在显示。修正为联合判定后，再加启动安全窗口和稳定采样；自动切换不再把仅投影仪布局保存为 Windows 的长期基线。

用户提出“搞个计划任务吧”，于是从旧 Run 自启迁到 ProgramData 的固定程序路径和计划任务，配置登录启动、失败重试及每五分钟补启动。实际终止进程后观察到任务恢复，用户也确认插线后显示正常，原 HDMI 1 与 Home 往返正常。没有把任务注册成功写成做过 Windows 整机重启测试。[事故与恢复边界](07-recovery.md)

## 11 月 24 日 HDMI 2 和 280 Hz 是最后补齐的一轮

改接 HDMI 2 后，先处理了插线黑屏，用户确认保持插线也恢复画面。随后把电脑源改为 2，实际状态读回和实体往返均正常。但用户指出返回显示器后变成 60 Hz。

历史快照和当前模式核对到 G27P6M 原本是 2560×1440、279.961 Hz。旧代码切到未启用的屏时让 Windows 自动选择模式，可能回落到 60 Hz。新版保存每块屏的完整单屏 timing，按当前路径和适配器编号重新绑定后严格验证、恢复。用户复测回复正常，回读也保持约 280 Hz。当前投影端记录的是 3840×2160、60 Hz，没有套用旧 HDMI 场景的 120 Hz。[本轮脱敏验证](../data/hdmi2-validation.json)

## 暂停和未完成的分支仍保留

| 分支 | 对话中的决定或最后结果 |
|---|---|
| 修改固件、刷 boot 或安装通用 root 管理器 | 讨论和检查过，最终没有实施刷写 |
| Google 登录与设备认证 | 连通探测改善，账户登录和认证未完成验证 |
| Apple TV 正片 | 应用可启动，播放失败仍未解决 |
| 语音切换信号源 | 代码加载过，用户叫停后没有完成实体验收 |
| 微信输入法借遥控器麦克风 | 32 位核心引擎不兼容，用户说“先不搞输入法了”，测试包卸载，原搜狗电视输入法保留 |
| 桌面和启动速度大幅优化 | 检查和小范围调整做过，没有测得明显提速或可靠的桌面 FPS 提升 |

这些经历形成的工作方式是：先检查和备份，说明原因、后果与步骤，做可恢复的短时试验，再让实体操作确认，最后持久化并验证重启。公开归档保留结论和自写代码，订阅、私有配置、原始聊天、截图及厂商程序不上传。
