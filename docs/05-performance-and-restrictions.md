# 性能体检与厂商限制

先测量，再决定保留哪些修改。结果是：做了小范围调整，但没有找到靠几条通用 ADB 命令就能明显改善桌面的方案。

## 当时的资源情况

- 系统可见约 1.81 GiB RAM，最初 MemAvailable 约 569 MiB，内存和 I/O PSI 压力较低。
- `/data` 约 50 GB 可用，仅使用约 4%；清缓存不是当时主要方向。
- 采样 CPU 总利用率约 12%～13%，不能只看约 37 的 load average 就说 CPU 跑满。
- 最高 CPU 频率 1.53 GHz，schedutil；温度读数约 60°C、热状态 0。没有锁高频或关闭热保护。
- 显示输出 3840×2160 / 60 Hz，桌面逻辑大小已为 1920×1080；没有继续强降分辨率。

## 编译与动画

桌面原状态 `extract`，BT、网易爆米花原状态 `verify`。定向请求 `speed` 后，BT 和网易最终读到 `speed`；桌面仍为 `verify`。

查明桌面 4.1.7 带 `DEBUGGABLE` 标记，Android 的 PackageDexOptimizer 会把可调试应用转到安全编译过滤器。这个问题来自当前 APK 属性与 Android 行为，不能当作“厂商禁止第三方桌面优化”的证据。

保留窗口打开、窗口切换动画 0.5 倍；曾把全局动画时长也调为 0.5，帧统计变差后恢复默认。没有把动画变短等同于 FPS 变高。

## 启动测量

每个应用三次 `am start -W -S`，保留文件缓存，统计进程冷启动的 `TotalTime` 中位数，不代表联网内容加载完成。

| 应用 | 调整前 | 后台编译结束后 | 结论 |
|---|---:|---:|---|
| 当贝桌面 | 2833 ms | 2795 ms | 差异约 1.3%，未证明明显改善 |
| BT | 994 ms | 1031 ms | 未测得改善 |
| 网易爆米花 | 1054 ms | 977 ms | 约 7.3% 差异，三次样本不足以下强结论 |

第一组修改后测试与后台编译重叠，已作废。完整脱敏数值见 [data/benchmarks.json](../data/benchmarks.json)。

最初累计 70 帧中有 13 个 janky 帧，出现过 450 ms 长帧；充分运行后的焦点基线为 411 帧、1 个 janky 帧。后续不同进程、缓存和后台负载下比例波动，未控制所有变量，所以不把比例直接相减来宣传提升。

## 固件里确认存在什么

| 机制 | 证据与当前边界 |
|---|---|
| 额外后台强停 | OomAdjuster 存在约 5 秒后台超时和 forceStopPackage 分支。总开关已关闭，但独立名单不因此自动消失 |
| 指定应用黑名单 | `sys_admin_pkg*.json` 分别有广播、后台运行、后台进程名单，涉及腾讯视频、PPTV、搜狐、芒果等部分包名。没有逐个复现所有名单效果 |
| 自家组件优先保留 | `sys_pkg_adj.json` 对原桌面、Etna、语音、统计等设置 OOM 优先级；第三方桌面已是 mHomeProcess，但待遇不完全相同 |
| 启动白名单及延迟 | ProcessList、BroadcastQueue 调用厂商配置，存在按包名分配的启动和广播处理；可能用于开机负载控制，不单凭存在就认定恶意 |
| 原厂桌面启动干预 | 之前实机记录过原厂 SplashActivity 被显式启动，单看默认 HOME 解析不足；已补充处理 |
| 指定应用强制 720p | 代码和 XML 名单存在，但对应属性未设置、代码默认 false，本机当时未启用。指兼容界面渲染，不等同于把视频源改成 720p |
| 应用列表过滤 | 配置为 true，发现过滤辅助函数；尚未证实实际调用链或具体隐藏效果，未擅自改动 |
| 32 位固件 | ABI 不含 64 位，纯 64 位 APK 不能直接装。不是改一个属性就能变成 64 位系统 |
| 统计等后台组件 | 统计进程与 DataReport 数据库存在；未抓取上传内容，不能据此断言窃取了什么数据 |

自家组件的 OOM 差别待遇属于明确可见的策略。其他一些机制可能同时承担资源管理用途，需要按场景验证，不能为了“去限制”全部关闭。

## 为什么没有直接大卸载

原桌面、Etna、统计、语音、设置等共享 UID 1000，原桌面还提供被其他组件使用的 ContentProvider。粗暴按 UID 限制、停整包可能波及其他功能。

抽样独占/分摊后的 PSS：统计约 25.6 MiB，原桌面约 74.0 MiB，Etna 约 56.0 MiB。RSS 有共享页，不能把所有进程 RSS 相加后说它们独占了那些内存。

优先继续测试非调试桌面构建或更轻桌面，再按实际使用功能逐项检查推荐、IoT、投屏、统计组件。当前没证明“卸载某一包必然流畅”，所以没有这么写，也没有批量停用。

参考：[dumpsys / gfxinfo](https://developer.android.com/tools/dumpsys)、[ART 编译过滤器](https://source.android.com/docs/core/runtime/configure)。
